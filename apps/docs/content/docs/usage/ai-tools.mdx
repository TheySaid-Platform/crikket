---
title: AI Tools (MCP)
description: Let Claude Code, Cursor and other MCP clients read your bug reports while they debug.
---

Crikket runs a remote [MCP](https://modelcontextprotocol.io) server. Once it
is connected, you can paste a bug report link into your AI tool and it can read
the report's details, the user's steps, console logs and network requests on
its own.

All tools are read-only. They never change a report.

## Create an Access Key

1. Open **Settings → AI Tools (MCP)**.
2. Click **Create key**, give it a name (for example `claude-code-laptop`) and
   choose when it expires.
3. Copy the key. It is shown only once.

A key belongs to you and to the organization that was active when you created
it. It can read exactly the bug reports you can read in that organization, and
it stops working when you revoke it, when it expires, or when you leave the
organization.

## Connect Claude Code

```bash
claude mcp add --scope user --transport http crikket https://api.example.com/api/mcp \
  --header "Authorization: Bearer <your-access-key>"
```

Use your Crikket server URL. The settings page shows the exact command with
your URL filled in. `--scope user` makes Crikket available in every project.
The command contains your key, so your shell saves it in its history; clear
that line afterwards if that matters to you.

Access keys work with clients that let you set a header, such as Claude Code
and Cursor. Claude.ai and Claude Desktop custom connectors need MCP OAuth
sign-in instead, which Crikket does not support yet.

## Connect Cursor

Add this to `.cursor/mcp.json` (or `~/.cursor/mcp.json` for every project):

```json
{
  "mcpServers": {
    "crikket": {
      "url": "https://api.example.com/api/mcp",
      "headers": {
        "Authorization": "Bearer <your-access-key>"
      }
    }
  }
}
```

Any other MCP client that supports Streamable HTTP and custom headers works the
same way.

## Tools

| Tool | What it returns |
| --- | --- |
| `get_bug_context` | Start here: details, steps, the first error of each tab with its stack, console errors and warnings, failed requests with bodies, and moments worth seeing |
| `list_bug_reports` | Reports in your organization, filtered by text, status, priority or visibility |
| `get_bug_report` | One report's details, device, open tabs and a link to the video or screenshot |
| `get_reproduction_steps` | What the user did, in order |
| `get_console_logs` | Console output, filtered by level, text or tab |
| `get_network_requests` | Network requests, filtered by status (`"4xx"`, `"500"`), method, host or content type, with bodies of failed requests |
| `get_network_request_details` | One request's headers and bodies |
| `get_video_frames` | Still images from the video: an overview grid of the whole recording, frames at times or steps (`"1:05"`, `45000` ms, `"step:7"`), or evenly spaced frames in a window |

Every tool takes either a report id or its share link
(`https://app.example.com/s/<id>`). Times in results are `offsetMs`,
milliseconds from the start of the video, and `get_video_frames` accepts
them as they are. It returns up to 12 images per call; the AI's own model
looks at them. The recording's audio is not available to the AI.

If the recorder captured more than Crikket stored (over 2,000 logs, steps or
requests), `get_bug_context` says so, so the AI does not read a missing error
as proof there was none. Typed text is never recorded, only its
length, and sensitive headers such as cookies and authorization are removed
when a report is captured.

## Example

> Debug this bug: https://app.example.com/s/gVQoTvqv0vRo

The AI calls `get_bug_context`, reads the failed requests and console errors,
and can then open a single request with `get_network_request_details` or look
at the screen around the failure with `get_video_frames`.

Frames are cut on the server with ffmpeg, which the server image installs. On
a self-hosted server without ffmpeg, `get_video_frames` says it is not
available and the other tools keep working.
